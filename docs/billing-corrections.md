# 计费修正：规则、原始事实与本地重算

## 设置与适用范围

系统设置中的一个“计费修正”卡片包含三个独立开关与规则弹窗。规则按顺序匹配；同一修正类别只使用第一条命中规则，三个类别之间叠加。模型匹配不区分大小写，只有 `*` 是通配符，其余字符按字面匹配，不执行用户输入的正则表达式。每类最多 100 条规则，空规则列表等同于该类无匹配项。

| 类别 | 默认模型匹配 | 默认参数 | 生效条件 |
| --- | --- | --- | --- |
| FAST | `*` | Sub2API 2 → 目标 2.5 | `priority` 或 `fast` 服务档位 |
| 长上下文（设置名“双倍倍率修正”） | `gpt-5.6*`、`gpt-6*` | Sub2API 2 → 目标 1 | 上游明确标记已使用长上下文计费，或兼容判断满足阈值 |
| 模型计费倍率 | `gpt-6*` | 1.8 | 模型命中，与 FAST、上下文无关 |

这组新默认值和两条内置公告来自项目运营策略与需求中指定的社区研究，**不是对 OpenAI 官方计费规则的独立证明**。在 Sub2API 已配置对应倍率时，需要根据实际部署调整本地参数，避免重复修正：上游已把长上下文改为 1，则源倍率和目标倍率均设为 1；上游已包含 GPT-6 的 1.8 倍，则本地模型倍率设为 1。

CPA 使用独立的本地价格体系，不应用这些 Sub2API 修正规则。普通用户不能修改系统计费设置，已有页面、账号、参与者可见性规则仍然有效。

## 金额的唯一计算顺序

固定按 **FAST → 长上下文 → 模型倍率** 逐请求计算。在选定的实际/标准成本口径下，设原始金额为 `R`：

```text
F = FAST 目标倍率 / FAST Sub2API 倍率；未命中或关闭时为 1
L = 长上下文目标倍率 / 长上下文 Sub2API 倍率；未生效时为 1
M = 模型倍率；未命中或关闭时为 1

A             = max(0, R + round6(R × (F - 1)))
B             = max(0, A + round6(A × (L - 1)))
C             = max(0, B + round6(B × (M - 1)))
FAST 修正     = A - R
长上下文修正  = B - A
模型倍率修正  = C - B
修正合计      = FAST 修正 + 长上下文修正 + 模型倍率修正
最终金额      = C = R + 修正合计
```

金额使用 Decimal，增减额逐阶段按六位小数、ROUND_HALF_UP 舍入。极小原始金额降倍率时，舍入后的扣减可能超过该阶段余额，因此每阶段将余额下限设为零，再计算有符号增减额；这类不足一百万分之一美元的边界保留必要精度，以同时保证最终成本非负和三项之和严格守恒。恒等倍率不改变原始成本的有效精度。三项明细是固定顺序下的**边际增减额**，而不是三个分别作用于原始金额的独立增量。不得截断负修正。

例如原始实际成本 100 的 GPT-6 FAST 长上下文请求，默认三项依次为 `+25`、`-62.5`、`+50`，修正合计 `+12.5`，最终为 `112.5`。把模型倍率改为 1 后，最终为 `62.5`，修正合计为 `-37.5`。两种情况下明细之和都严格等于合计。

## 余额建议的扣费口径换算

测算继续使用修正成本推断容量与百分比归属，但 Sub2API 钱包按实际扣费成本消耗。`billing_correction.settlement.balance_conversion_factor` 返回 **实际扣费金额 / 修正后的测算金额**；余额建议在生成时乘一次该系数，再应用安全系数和分币舍入。它是“预计应设置的余额”，不是追加充值金额。

- 优先使用本人在对应账号、当前归属区间内的已采集请求样本；本人没有消费样本时使用同账号同期样本。按金额加权，不取逐请求倍率的算术平均。
- `actual` 与 `standard` 两种测算口径都换算到原始 `actual_cost`。因此全部本地修正关闭但使用 `standard` 时，仍可能需要标准成本到实际扣费的换算；不会重复剥离已经包含在 actual 中的用户/分组倍率。
- 旧 FAST 汇总没有完整请求时，使用已知的区间成本与修正差额；实际口径从区间 selected 减去同期修正恢复 raw。标准口径优先使用同区间个人实际/标准成本端点，否则估计采用账号实际/标准端点。不能把整周期 `raw_selected_cost` 直接与人工起点后的 `selected_cost` 相除。
- 本人与账号都没有可用样本或可推导成本时，以 1 作为初始估计；后续采样提供消费数据后更新。CPA 不应用这套 Sub2API 换算。
- 动态快照的建议点值、概率余额区间、确定性余额区间及差额统一为钱包口径。模型容量、成本、百分比归属不变；金额范围以估计倍率为条件，并不包含未来用法变化的不确定性。
- 池聚合从模型容量和权益重新计算每个来源的带符号净头寸，逐来源换算后再跨账号抵扣、汇总和应用安全系数。`net_position_*`、`contribution_*`、`recommended_balance_*` 是钱包口径；capacity、selected cost、entitlement 指标继续是测算口径。通知、前端和手动/自动写入共用聚合建议，不二次换算。

例如非长上下文 GPT-6 FAST 的原始 actual 成本为 100，修正后成本为 225，换算系数为 `100 / 225`。统一倍率场景下，平均恒定聚合建议从修正口径的 1941.40 换为钱包口径的 862.84。粒子滤波还有固定容量先验与边界，切换修正后不保证与关闭修正时的建议完全相同。

历史消费结构只是未来消费的估计；模型、FAST、长上下文或上游计费变化后，估计随新区间请求样本更新。该估计面向钱包余额计费，不推断订阅扣费与钱包扣费的混合比例。建议优先在 Sub2API 统一倍率并使用实际扣费口径，确认某项上游倍率生效后再关闭本地对应修正。以调整后的观测建立新测算起点，避免混用新旧扣费历史。

此次派生版本为 `particle_filter_v10`，粒子随机种子版本保持不变。容器启动时的 `replayobservations` 会识别旧版本并本地重放；非容器运行在升级后执行 `uv run python manage.py replayobservations`。原始请求、已确认的历史余额操作和用户设置不改写。

## 长上下文的事实来源

首先使用上游原始 `long_context_billing_applied` 布尔值。明确的 `false` 优先于 Token 推断，不能因为 Token 数多就擅自除以 2；明确的 `true` 使用配置的源/目标倍率。

旧版上游未返回该字段时，才使用输入 Token、缓存创建 Token、缓存读取 Token 之和进行兼容判断。默认严格大于 `272000` 才命中，输出 Token 不计入。阈值可按模型规则配置。已知的非负 Token 小计已经超过阈值时，即使其他项缺失也足以判定；否则缺少必要字段会标记为“上下文事实不足”，而非假定未命中。不存在的布尔值与 Token 数保留为 null，不转成 false 或 0。格式非法的上游事实会拒绝写入。

Sub2API 的原始字段与 Token 基准参考其 `backend/internal/handler/dto/types.go`、`backend/internal/service/billing_service.go`（研究时版本 `ab99d56e9626e6cd731592dae8553c9758a0efa2`）。阈值是兼容参数，不是对所有网关版本或未来模型的保证。

## 存储与本地重算

迁移 `0049_traceable_billing_corrections` 是增量迁移，无上游请求、无历史金额覆盖。

- `ObservationBillingCapture`：一个观测区间的起止时间、完整请求数与 schema version。即使日志为零条，也有完成标记。
- `BillingUsageFact`：区间内原始请求 ID、上游用户 ID、时间、模型、档位、实际/标准成本字符串、可空 Token 数与长上下文计费标记。按区间和原始请求 ID 唯一。
- `APIUsageRequestFact`：账号与请求 ID 唯一的 API Key 用量原始事实缓存。只保存 Key 的 ID 和展示名称，**不保存 Key 原文、请求内容或凭据**。

新增两种修正不建立“修正金额事实表”。读取、重放、模型分配、统计展示均通过同一计算器投影；规则摘要和逐模型的倍率/证据来源在详情响应中动态返回。原有 FAST 聚合字段仅为历史兼容保留，已有原始捕获区间优先使用原始事实。

采集原始请求不以开关状态为条件：即使暂时关闭全部修正，也保留将来开启或添加模型规则所需的数据。这会比只保留 FAST 汇总占用更多数据库空间，应纳入数据卷和备份容量规划。

保存任意一种修正规则会进入项目现有的账号写入隔离、事务与历史重放链路。原始观测、原始请求、周期边界和百分比不变；派生累计金额、参与者分配与两种额度模型结果按当前规则重算。原始事实完整性验证失败时设置保存回滚，不进行部分静默重算。重算没有上游请求，但计算时间仍取决于历史规模，并非保证常数时间或瞬时完成。

API Key 当前周期统计具有独立的一小时缓存有效期。有可用原始缓存时，仅修改规则、成本口径不会使其重新下载整周期；下一次读取直接从去重原始请求重新投影。正常过期刷新仍会读取上游。老版本只有派生缓存而无原始日志的条目可能在首次查询时刷新一次。快照中保留的旧汇总字段是可替换缓存，新三项明细不持久化为权威事实。

## 升级前的数据边界

升级前只有 FAST 汇总金额的观测，无法仅凭汇总恢复模型分布或上下文 Token。此类区间保持历史 FAST 值，返回 `legacy_fast_only=true`、`correction_facts_complete=false`、`correction_calculated=false`（旧的 `fast_correction_calculated` 仍保留 FAST 专属语义）；不伪造新两类修正，也不反向构造请求。

原有 `/fast-correction` 详情和 `/fast-correction/calculate` 补采路由保留，现统一支持三项修正。观测列表中缺少原始捕获的记录显示可点击的“未计算”，**包括已有 FAST 汇总但缺少两项新修正依据的旧区间**。旧汇总仍可通过同一列的“已有明细”查看；管理员也可以在详情中点击“从上游补算此区间”。普通用户只能查看，不能请求上游或改写数据。

补算是显式管理员操作：只读取所点区间的原始请求；旧记录优先沿用已保存的修正起点，新缺失记录采用同一周期上一条原始观测（包含被排除的观测），周期首条使用官方窗口起点。日志读取包含严格分页和半开区间校验；上游只支持日期筛选时，获取涉及日期的日志后再按本地区间精确裁剪。采集成功后，事务内保存原始请求、更新兼容 FAST 汇总，并本地重放受影响的后缀；页面同时刷新金额和相关结论，不重新抓取整个周期或其他观测区间。队列中的每个区间独立处理，失败可重新点击。

已经存在的原始捕获（包括零请求区间）不会被新查询覆盖，重复点击直接读取本地；损坏的原始捕获会报错，不以重新抓取覆盖审计证据。上游失败或重放失败均不写入半成品、不清空旧 FAST 金额；旧记录已有精确请求数时，补回的数量必须一致，防止上游清理日志后把缺失误作零请求。没有保存任何历史数量的区间只能验证上游返回的分页完整性，无法独立证明上游从未删过日志。

补齐一次原始事实后，再修改倍率仅需本地重算。上游已清理或从未提供的模型/Token 事实不能凭空恢复；即使请求捕获完整，仍缺少模型或长上下文判断字段的请求会继续明确警告，不将它们误说成已证实无需修正。

账号状态的上游实时总额可能晚于本地最后一次采样；页面标注修正采集截止时间。三十天汇总的原始请求按时间裁剪，旧汇总无法拆分时保持旧兼容口径并提示事实不完整。

## API 与前端兼容

观测、成本依据、账号状态、API Key 统计增加以下金额字段：

```text
fast_correction_usd
long_context_correction_usd
model_correction_usd
correction_total_usd
```

`fast_correction_usd` 仍仅代表 FAST；新总额必须读取 `correction_total_usd`。既有详情路由名称和 operation ID 保持兼容，但详情中的通用 `correction_usd` 现在代表修正合计。OpenAPI 已追加 schema 与语义说明。

列表只展示一列修正合计，点击打开三项明细；零额也可展开，负额带符号。账号状态、API Key 统计、恒定模型/时变模型/每日结算依据复用同一展开组件。金额明细最多显示六位小数，避免仅因显示四舍五入掩盖细小修正。

演示站保留原有合成历史，将其明确标注为旧版 FAST 汇总，不声称演示历史含有不存在的原始 Token 事实。演示状态版本升为 15，以加载新的默认设置。演示中的点击补算只模拟状态转换，不访问上游，不代表恢复了真实请求。

## 自动检查与人工审阅路径

```bash
cd backend
uv run pytest
uv run python manage.py makemigrations --check --dry-run
uv run python manage.py check
cd ../frontend
pnpm check
pnpm build
```

专门的后端用例验证三段金额恒等式、负额、两种成本口径、规则优先级、上下文标记与边界、原始数据完整性、迁移不改旧记录，以及规则保存时禁止构造 Sub2API 客户端仍能完成两种额度模型的本地重放。API Key 缓存测试验证重复请求去重、规则改变不重新拉取、矛盾事实写入回滚。

`Billing corrections browser regression` GitHub Actions 工作流使用只读仓库权限，在隔离临时 SQLite 中生成测试账号和数据，验证设置弹窗、取消/排序、非法倍率、真实设置保存、观测三项负额明细与 390px 窄屏。截图和结果文件可供审阅；不会上传数据库、真实密钥或生产凭据。测试脚本为 `scripts/billing_browser_smoke.py`，浏览器依赖仅属于 CI 开发检查，不进入运行镜像。

人工检查建议：备份数据库后升级；确认仅一个计费修正卡片和两条新增未读公告；检查默认参数；在同时有 FAST、长上下文、GPT-6 的原始区间中核对 `100 → 112.5` 示例；将模型倍率设为 1 并核对 `100 → 62.5`；确认观测与结论依据均可展开、旧区间有证据不足提示、只读用户不能写入设置、CPA 数字未被应用 Sub2API 修正。

回退前保留升级前备份和当前数据库副本。该迁移新增字段与事实表，回退应用代码可使用升级前备份；不要在唯一生产数据库上直接反向迁移并删除新采集的原始事实。

### 定向补算回归

`tests/billing_correction/test_backfill.py` 覆盖新缺失/旧 FAST-only、两种成本口径和额度模型、精确区间、后缀刷新、补齐后离线调倍率、失败回滚与重试、零请求、幂等、旧日志数量不一致、权限及 CPA 隔离。浏览器回归使用仅绑定本机的合成 Sub2API HTTP 服务，实际点击“未计算”和详情补算按钮，验证从真实后端发起只读日志请求、失败后可重试以及 UI 后缀刷新。
